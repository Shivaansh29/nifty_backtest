# M2: Reference data

## Demo

```bash
uv run nifty-backtest download-index   # NIFTY 50 OHLC, India VIX, NIFTY 50 TRI, NSE holiday lists
uv run nifty-backtest build            # option rows (now with lot sizes) + index table
uv run nifty-backtest expiries         # reports/expiry_calendar.csv

```

## What was built

| Where | What |
|---|---|
| `reference/special_sessions.csv` | All 10 weekend/holiday sessions in the window, each with its NSE circular and whether it was short |
| `reference/lot_sizes_legacy.csv` | One sourced row: lot 50 for every NIFTY contract, Oct 2021 – Dec 2023 (NSE/FAOP/47854) |
| `marketdata/lots.py` | A lot size, and where it came from, for every stored option row |
| `marketdata/trading_calendar.py` | Trading days, special sessions, real expiries, and the expiry calendar with entry days |
| `marketdata/settlement.py` | Final settlement level per expiry, and intrinsic value |
| `marketdata/indices.py` | NIFTY 50 OHLC + India VIX (NSE), NIFTY 50 TRI (NSE Indices), with an archive gap-filler |
| `marketdata/holidays.py` | NSE's official F&O holiday lists, to reconcile every day with no session |

New CLI commands: `download-index`, `expiries`, and `build --rebuild`.

## Results on the real data (report of 2026-10-19)

- **Holidays:** all 71 weekdays without a session are official NSE F&O holidays, so there are
  **0 data gaps**. The only official holiday that had a session is the Muhurat day, 21 Oct 2025.
- **Special sessions:** all 10 are listed, and every one is present in the data. Volume backs
  up the circulars independently:
  - the short sessions traded **8–27%** of the surrounding median;
  - the full Saturday/Sunday sessions traded 55–157%.
- **Expiry calendar:** **263 real expiries, all `ok`**, and every one has a known lot size at
  entry. One entry carried a re-dated label: 28 Jun 2023, entered on 23 Jun while that day's
  file still said 29 Jun.
- **Lot sizes, nearest expiry, whole window:**

  | Lot | From | Source |
  |---|---|---|
  | 50 | Oct 2021 | sourced table, then overlap UDiFF rows |
  | 25 | 26 Apr 2024 | |
  | 75 | 27 Dec 2024 | |
  | 25 | 24–30 Jan 2025 | |
  | 75 | 31 Jan 2025 | |
  | 65 | 31 Dec 2025 | |

  0 option rows lack a lot size.
- **Index data:** all 1,251 trading days have NIFTY OHLC, VIX and TRI. One day, 2 Mar 2024, is
  absent from NSE's API and was filled from NSE's archive file, marked as such.
- **Two independent NSE sources agree:** UDiFF's underlying price equals the index close on all
  566 UDiFF days.
- **Settlement (trap 3):** on **all 263 expiries**, every expiring contract carries one settle
  value, and it equals NSE's official NIFTY close exactly (largest difference 0.0).

## Key design decisions

1. **Primary sources only, read in full.** The lot-size row and all 10 special sessions cite NSE
   circulars, and I read each PDF rather than trusting its title. This mattered: 20 Jan 2024's
   circular *title* says DR drill, but NSE/MSD/60340 withdrew that plan and made it a
   **full** session.
2. **Lot size is per contract per trade date, and labelled with its source.** Each row's lot size
   comes from one of three places, and `lot_size_source` records which:
   - `udiff`: the UDiFF file itself;
   - `udiff_same_day`: on overlap days, the same day's UDiFF file, contract by contract;
   - `reference_table`: the sourced table.

   The 2024 change (50 → 25 on 26 Apr) needed no table at all, because the overlap data shows it.
   If no source exists, the lot size stays empty and M3 skips that week. It never guesses.
3. **Real expiries come from behaviour, not from printed dates.** An expiry counts only if its
   contracts traded on that day. The calendar keeps the date printed on the entry day next to the
   real one, and accepts the difference only if that printed date is a known re-dated date.
4. **Entry = N *full* sessions before the real expiry.** Short sessions don't count, and they are
   never entry days. The calendar also flags any expiry that wouldn't be the nearest one on its
   entry day (none exist at N = 3).
5. **The settlement level is read, then cross-checked.** Expiring contracts must agree on one
   settle value, and the code raises an error if they don't. The report then compares it with
   NSE's official close.
6. **Monthly API requests and a coverage check.** NSE's price API silently returned only 70
   rows for a one-year request. Fetching one month at a time and checking every trading day turns
   that silent truncation into a visible gap.
7. **The gap-filler is marked and its precision limit stated.** 2 Mar 2024 comes from NSE's archive
   file, with `nifty_vix_source = nse_archive`. The archive rounds VIX closes to 2 decimals
   (18 May 2024: 20.53 vs the API's 20.525), and the code says so.
8. **Validation is strict, and relaxed only on evidence.** The TRI feed printed "NIFTY 50"
   instead of "Nifty 50" on 23–24 Dec 2025. I checked that response by hand before making only
   the *name* comparison case-insensitive. The date and duplicate checks stayed strict.

## Explain-back questions

1. How does the calendar decide that 28 Jun 2023, and not 29 Jun, was a real expiry? What would
   go wrong in M3 if it trusted the date printed on the entry day?
2. Why does 24–30 Jan 2025 trade 25 units when the weeks around it trade 75? Where does the code
   get that number, and what happens if no source exists?
3. On expiry day, why must every expiring contract show the *same* settle price, and what does
   the code do if they don't?
4. Why are Muhurat and DR-drill days excluded when counting "3 trading days before expiry", but
   20 Jan 2024 isn't?
5. NSE's price API returned 70 rows for a one-year request without any error. How does M2 make
   sure a problem like that can't slip through unnoticed?
