# M9: NIFTY iron condor study

## Demo

```bash
uv run nifty-backtest study docs/research/m9_plan.toml      # about 30 minutes, 42 runs
uv run nifty-backtest serve                                 # then open the research page
```

- The study refuses to run unless `docs/research/m9_plan.toml` is frozen and both it and
  `docs/research/m9_iron_condor_plan.md` (the pre-registration) are committed and unchanged.
- It writes `studies/<id>/`: `study.json`, `report.md`, `comparison.csv`, `q1.csv`, `q3.csv`,
  `cost_grid.csv`, `sensitivities.csv`, and every run under `runs/`.
- On the dashboard, the study page shows the verdicts apart from everything descriptive, and a
  condor trade's drill-down shows all four legs and each leg's daily mark.

Checks:

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest
cd frontend && npm run typecheck && npm test && npx vite build
```

## The question and the answer

Does a weekly NIFTY iron condor have an edge after all costs, and does it improve on the short
straddle baseline (B0)? Three pre-registered variants were tested: short strikes at ATM ± 1.00,
0.75 and 1.25 × P (C1, C2, C3), where P is the ATM straddle premium, with wings 1 × P beyond.

- **Q2, the verdict: all three are inconclusive.** No variant's difference from B0 reaches a
  Holm-adjusted p below 0.05 (0.259, 0.259, 0.273). Every point estimate is negative in both
  periods (−4% to −7% of B0's premium per expiry), and every interval includes zero.
- **Q1: no edge demonstrated,** for B0 or any condor. Mean R_P is −1.5% to −2.5% of P per trade
  in development and +0.3% to +0.7% in validation, all with intervals that include zero.
- **Q3, descriptive only:** the condors roughly halve the worst trades and the drawdown, but
  give up most of the profit. Net profit relative to drawdown is lower than B0's for every
  condor in both periods.
- **Nothing is confirmed.** Validation was previously observed for the straddle and can only
  reject. The forward holdout (entries from 17 Oct 2026) has not been computed.
- **No variant is chosen.** The rule picks none, and choosing the one with the highest
  historical profit would be exactly the selection the pre-registration forbids.

### Provenance: the working tree was not clean for 41 of the 42 runs

Every run records commit `f145430`, but `git status` was not clean when 41 of them were saved,
so their manifests correctly say `uncommitted_changes: true`. **The study must not be described
as generated from a clean tree.** What was different:

| Runs | Working tree when the run was saved | Code that produced it |
|---|---|---|
| 1 (B0 development, 12:10:14) | clean | `f145430` |
| 33 (12:10:49 – 18:20:06) | one untracked file, `docs/milestones/M9.md` (this notes draft, written at 12:10:14) | `f145430` |
| 8 (the last C1 cost-grid cells, 18:21:18 – 18:28:32) | that file plus the uncommitted debit-spread edits to `engine/multileg.py`, `strategies/base.py`, `strategies/iron_condor.py` (saved 18:20:58) | `f145430` |

Why the code is `f145430` in every case:
- The study is one Python process. It starts no other Python process; its only subprocess is
  `git` (for the status). Python never re-imports a module it has already loaded, and the three
  edited modules were all imported when the study started at 12:09. The two modules it imports
  late (`condor_report`, `report`) were unchanged.
- **Checked by reproduction:** 18 runs (all 10 verdict-bearing variant runs and all 8 runs saved
  after the edits) were re-run from a clean export of `f145430` (`git archive`) and compared
  file by file. **All 18 are identical** in `trades.csv`, `marks.csv`, `equity.csv`,
  `skipped.csv` and, for the condor runs, `legs.csv` and `leg_marks.csv`. The other 24 runs
  (the B0 grid and the earlier C1 grid cells, all saved before the code edits) were not re-run.

is net points per unit ÷ P (%), R_ML net points ÷ maximum loss (%). Worst 5% is the mean of the
worst 5% of expiries in % of B0's premium for the same expiry, the Q2 tail measure. The
variants and B0 trade the same expiries with the same costs and capital.

How to read Q3:
- **The condors cap the tail.** The worst week costs at most about one P (R_P −80% to −97%),
  against 2.0-2.6 P for the straddle, and the worst 5% of weeks lose about half as much.
- **They also give up most of the profit.** Net profit per rupee of drawdown is lower than
  B0's for every condor in both periods.
- **Rupee totals mix lot sizes** (25 to 75 over the window), so they weigh years unequally; the
  lot-free drawdown does not.
- These differences are descriptions, not evidence: Q2 found no measurable difference.

## Validation of the outputs (done before reading the verdicts)

All passed:
- **Trade counts** match the frozen coverage exactly: 156 and 106 for B0, C1, C2, C3 and C1-R
  development; 105 for C1-R validation. The only skipped week in any variant run is C1-R's
  24 Mar 2026 (zero volume).
- **Costs and P&L, recomputed independently** for every C1, C2, C3 and C1-R trade from its legs
  with a separate rate lookup: fills, intrinsic values, expiry statuses, credit, charges and
  net P&L all agree within ₹4 × 10⁻¹². Each trade's legs add up to the trade.
- **Same dates:** every condor traded exactly B0's expiries in both periods.
- **B0 reconciles with the M6 reference run:** removing IPFT from GST's base, B0's 262 trades
  equal the reference run's net P&L within ₹7 × 10⁻¹². B0's engine path is also still byte for
  byte identical to that run (regression test).
- **Statistics re-derived:** Q1 means, the C1 paired mean, every t-statistic, the Holm adjustment
  and each development verdict were recomputed from the run files and agree.
- **Hand traces:** the two trades the plan's rule picked (NIFTY-2021-10-07, no bought leg in
  the money; NIFTY-2021-12-09, long call exercised) match a hand calculation from the raw NSE
  files to 10⁻⁹ rupees (`tests/test_realdata_m9.py`).
- **No date after validation:** the latest expiry in any run is 13 Oct 2026.
- **Maximum loss:** the payoff-based function added after the study (below) returns exactly the
  saved value for all 3,143 condor trades in the 24 condor runs. An earlier comparison appeared
  to show 63 differences of about 3 × 10⁻¹⁴ points; they came from pandas' default CSV parser,
  which can read a float back one unit in the last place off. Read with exact round-trip
  parsing, there are none.


## Implementation note: a separate signed path

The plan (§9.2) described generalising the straddle's code path. It was implemented as a separate
signed multi-leg path next to an unchanged straddle path, because that is the most direct way to
guarantee B0's byte-for-byte reproduction. The rules and numbers are the plan's; only where the
code lives differs. The debit-spread check above shows the new path is general.

## Key design decisions

1. **One new code path instead of editing the straddle's.**
   - The pre-registration requires B0 to reproduce its reference run byte for byte.
   - The safest way to guarantee that is to leave the straddle path exactly as it was and add a
     general signed path for multi-leg strategies, chosen by a class flag (`multi_leg`).
   - The new path is the one-time generalisation the spec change allows: any later debit
     spread or strangle uses it with no engine change.
2. **Signs instead of special cases.** Every leg carries s = +1 (sold) or −1 (bought). Credit,
   value at expiry, P&L and marks are all Σ s × value, so one set of formulas covers every
   structure, and a straddle would give the same numbers.
3. **Costs leg by leg, never netted.** Each order pays its own charges; beyond a long strike
   both legs are in the money and both pay settlement charges. The payoff is capped by the
   wing, the costs are not.
4. **No look-ahead for C1-R.** With strikes from the previous session, the strategy is given
   only the previous session's chain and NIFTY close. The legs it picks are then checked and
   filled on the entry day. A test changes every entry-day close and checks that no strike moves.
5. **The GST base is one plan-level setting.** IPFT in GST's base is unverified, so it is a
   setting (`gst_on_ipft`), off by default (every historical run is unchanged) and turned on
   once, for every run of the M9 study, so both sides of every pair share it. A variant that
   tries to set it is refused.
6. **Sensitivities are recomputed from the saved files.** Stamp duty, SEBI notional and the GST
   base are changed after the runs, from `legs.csv` and the trade logs, and the rule is
   re-applied to see what it would say. They never change a verdict.
7. **Debit structures work without another engine change (added after the study).** A
   synthetic bull call spread, written only in its test, exposed two credit assumptions in the
   multi-leg path: E8's positive-credit rule and "maximum loss = widest wing − credit". The rule
   is now declared by the strategy (`requires_credit`, set by the iron condor), and maximum loss
   is read off the payoff at 0 and every strike (blank when the loss is unbounded). The study's
   numbers do not change: every saved maximum loss is reproduced exactly. Committed separately
   as `418346e`.
8. **Condors cannot be launched from the CLI or the API.** Both default to "up to today", which
   would show forward-holdout results; tests guard this.

## Limitations

- **Small effects cannot be seen.** Paired differences have a standard deviation of 38-48% of
  B0's premium. With 156 development expiries the standard error of the mean is 3.0-3.9 points,
  so only differences of roughly 6-8% of B0's premium per expiry or more could reach
  significance, before the Holm correction makes the bar higher.
  Inconclusive means the data cannot tell, not that there is no difference.
- **Validation was seen before** (for the straddle), so it can only reject.
- **End-of-day data:** fills are at the official close, worse by an assumed slippage; real fills
  on four legs, especially the wings, may be worse. The cost grid shows how much that matters.
- **Unverified cost assumptions** remain (above). None can change a verdict here, but they are
  assumptions.
- **Dirty provenance** for 41 runs, as described; the code is shown to be `f145430` by argument and
  by reproduction, not by a clean `git status`.
