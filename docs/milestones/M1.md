# M1: Data ingestion

## Demo

```bash
uv run nifty-backtest download    # first run ~1.5 h (polite pacing); re-runs fetch only what's missing
uv run nifty-backtest build       # normalise both formats into Parquet
uv run nifty-backtest report      # writes reports/data_quality.md
uv run nifty-backtest sql "SELECT year(trade_date) AS yr, count(DISTINCT trade_date) AS days, count(*) AS rows FROM options GROUP BY yr ORDER BY yr"
uv run pytest -v                  # 31 tests; the 3 real-data tests skip if data/ is absent
```

## What was built

Everything lives in `src/nifty_backtest/marketdata/`:

| File | Job |
|---|---|
| `config.py` | One `DataConfig` object holding every date, path and politeness setting |
| `sources.py` | Builds each file's URL and cache path, and picks the format for each date |
| `download.py` | Polite, resumable downloader that logs every outcome to `data/raw/fo/download_log.csv` |
| `bhavcopy.py` | Parses both formats into one normalised schema of index-option rows |
| `store.py` | One Parquet file per trading day, plus a DuckDB `options` view over all of them |
| `quality.py` | The data-quality report, including a re-check of the legacy/UDiFF overlap |

The CLI gained four commands: `download`, `build`, `report` and `sql`.

## Results on the real data

From `reports/data_quality.md`, generated 2026-10-19 (the report itself is not committed).

**Coverage**
- All 1,845 calendar dates from 1 Oct 2021 to 19 Oct 2026 were checked.
- **1,251 trading days** were stored, the last on 16 Oct 2026.
- 594 dates had no session (404), 72 of them weekdays. M2 checks those weekdays against NSE's holiday list.
- **0 download errors.** 19 Oct is still pending: today's file wasn't published yet, and the
  next run re-checks it.
- Size: 1.3 GB of raw zips became **85 MB** of Parquet, holding 2.18 million option rows.

**Special sessions (trap 6).** Bhavcopies exist for:
- Sun 12 Nov 2023 (Muhurat);
- Sat 20 Jan, 2 Mar and 18 May 2024 (disaster-recovery drills);
- Sat 1 Feb 2025 and Sun 1 Feb 2026 (Budget days).

**Formats (trap 7)**
- **All 128 days** where both formats exist (2 Jan to 5 Jul 2024) agree exactly on every
  contract and every shared column. The largest turnover difference is ₹999, within legacy's ₹1,000 precision.
- The UDiFF volume-unit check gives a median ratio of **1.0** in 2024, 2025 and 2026.

**Zero-volume rows (trap 4).** 41–65% of rows, depending on the year. NSE lists many strikes
and far expiries that never trade.

**Three findings that change how M2 and M3 must work**
1. **Lot size can change during a contract's life.**
   - Example: the 27 Mar 2025 contract was 25 units until 26 Dec 2024, then 75 from 27 Dec.
   - NSE did this on 8 separate days, e.g. 27 Dec 2024 and 31 Dec 2025.
   - Consequence: for the 24–30 Jan 2025 trade week, the nearest contract was still **25**
     while the weeks around it were **75**.
   - One contract never has two lot sizes on the same day (0 cases).
   - So lot size depends on contract **and** trade date, not on the contract alone.
2. **A printed expiry date isn't proof the expiry happened.** NSE re-dates contracts, either
   to dodge holidays or at the Thursday→Tuesday switch. Seven stated expiries never arrived.
   - Example: on Mon 26 Jun 2023 the nearest contract still said **Thu 29 Jun**, but it
     really expired on **Wed 28 Jun**, because 29 Jun became a holiday.
   - So expiries are counted only where contracts traded *on* the date.
   - M2's calendar must map each stated expiry to the actual one.
3. **Expiry weekdays by year,** counting only real expiries:
   - Thursday weeklies until Aug 2025 (2022: 51 Thu + 1 Wed);
   - Tuesdays after the switch;
   - Mondays and Wednesdays where holidays intervened (2025: 1 Mon, 17 Tue, 2 Wed, 33 Thu; 2026 so far: 3 Mon, 38 Tue).

## Key design decisions

1. **The overlap settled what each column means.** Before writing the parser I downloaded days
   that exist in both formats and compared every NIFTY option contract. They matched 1:1, and:
   - legacy `CLOSE` = UDiFF `ClsPric`. It is *not* `LastPric`, which agreed only ~25% of the time.
   - `TtlTradgVol` = `CONTRACTS`, so both count contracts.
   - Settle, OHL and OI are identical.
   - Turnover is notional, and legacy rounds it to ₹1,000.

   The report re-runs this comparison every time, so it is evidence, not a one-off claim.
2. **Checks that work without an overlap.** After Jul 2024 there is nothing to compare
   against, so the report tests an accounting identity instead:
   turnover ÷ (contracts × lot × (strike + price)) ≈ 1. If NSE ever changed the volume unit,
   this ratio would move away from 1 and the report would show it.
3. **The parser stops rather than guesses.** It raises an error, and does not pick a value, if:
   - the two UDiFF expiry columns ever disagree;
   - a column goes missing;
   - a file contains the wrong trade date;
   - a contract appears twice.
4. **Every calendar date is tried.** Weekend and holiday sessions (Budget days, Muhurat)
   have bhavcopies too. A 404 is logged as "no session", which is different from a failed
   download. Old 404s are treated as final; 404s from the last 7 days are re-checked in case
   the file simply wasn't published yet.
5. **Downloads are atomic.** Each file is written as `.part` and renamed only once complete, so
   an interrupted run never leaves a half-file that looks finished. Content is also checked to
   start with the zip signature, because NSE sometimes answers "200 OK" with an HTML page.
6. **Raw files are kept whole.** Normalised data holds only NIFTY index options, but the raw
   zips hold every symbol. Adding BANKNIFTY later means re-running `build`, not re-downloading.
7. **One Parquet file per day.** Rebuilds are incremental, since only new or re-downloaded days
   are parsed. DuckDB reads the whole history through one glob pattern, without loading it
   into memory first.
8. **Zero-volume rows are kept and flagged, not deleted.** Deleting them would hide how
   illiquid much of the option chain is. Flagging them means later code can't mistake a stale
   price for a real fill (trap 4).
9. **Dates are parsed without the computer's locale.** Legacy dates like `27-Jun-2024` are
   parsed with an explicit month table, because `strptime("%b")` depends on the language setting.
10. **Tests:**
    - CI runs on synthetic files that copy NSE's exact headers, including the legacy trailing comma.
    - The 3 real-data tests compare against values traced by hand in the raw files, and skip when `data/` is absent.
    - A fake NSE server (`httpx.MockTransport`) tests the downloader with no network.

## Explain-back questions

1. Why does the normaliser read `ClsPric` and not `LastPric`, and how do we *know* that's right
   rather than assume it?
2. After July 2024 there are no legacy files to compare against. How does the report still
   detect a change in what the volume column counts?
3. A day returns 404. When does the downloader treat that as final, and when does it re-check
   it? Why does the difference matter?
4. Why are zero-volume rows kept, and what would go wrong in M3 if their prices were used as fills?
5. What does "atomic" download mean here, and what failure does it prevent?
6. (Bonus) Why can't the lot size simply be looked up by contract expiry, and why can't the
   expiry date simply be read from the entry day's file? Use the Jan 2025 and Jun 2023 examples.
