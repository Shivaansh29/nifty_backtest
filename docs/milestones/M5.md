# M5: FastAPI backend

## Demo

```bash
uv run nifty-backtest serve                  # http://127.0.0.1:8000; open /docs in a browser
curl -s http://127.0.0.1:8000/api/runs
curl -s http://127.0.0.1:8000/api/runs/20261022-191259-short_straddle/metrics
curl -s http://127.0.0.1:8000/api/runs/20261022-191259-short_straddle/trades/NIFTY-2026-05-12
curl -s -X POST http://127.0.0.1:8000/api/runs -H 'content-type: application/json' \
     -d '{"start": "2025-01-01", "end": "2025-03-31", "slippage_points_per_leg": 1.0}'
uv run pytest -v                             # 175 tests; 13 real-data tests skip in CI
```

## What was built

| Where | What |
|---|---|
| `api/schemas.py` | Pydantic models: one per saved file (config, manifest, trades, marks, equity, skipped, metrics, yearly, monthly) and the API's own shapes (run summary, run detail, trade drill-down, launch request, error body) |
| `api/store.py` | Finds run folders, reads each file and checks it against its model, works out each run's status |
| `api/launch.py` | `POST /api/runs`: the same steps as `nifty-backtest backtest` (resolve end date, run, save, compute metrics) |
| `api/app.py` | The FastAPI app: routes, error handlers, OpenAPI page |
| `api/errors.py`, `api/settings.py` | One error type for the whole API; where runs and data live |
| `cli.py` | `serve` command (`--host`, default 127.0.0.1; `--port`, default 8000; `--runs-dir`, default `runs`) |

**Endpoints**

All endpoints are under `/api`.

| Method and path | Returns |
|---|---|
| `GET /health` | status and version |
| `GET /runs` | every run, newest first, with status and headline numbers |
| `GET /runs/{run_id}` | status, config, manifest, files present, trade and skipped counts |
| `GET /runs/{run_id}/metrics` | `metrics.json` |
| `GET /runs/{run_id}/yearly`, `/monthly` | the M4 tables |
| `GET /runs/{run_id}/trades` | the trade log (all 45 columns) |
| `GET /runs/{run_id}/trades/{trade_id}` | one trade plus its daily marks |
| `GET /runs/{run_id}/equity` | the equity curve |
| `GET /runs/{run_id}/skipped` | skipped weeks |
| `POST /runs` | launch a run; returns 201 with the new run's summary |

**Dependencies:** FastAPI 0.143.0 and Uvicorn 0.54.0, both owner-approved.
- Both are 0.x, where minor releases may break things, so `pyproject.toml` allows only their
  0.143 and 0.54 series, and `uv.lock` pins the exact builds.
- FastAPI 0.143.0 was the newest release at least two weeks old.
- FastAPI also brings Pydantic, Starlette and `opentelemetry-api`, which FastAPI itself
  requires.
- httpx, already a dependency, serves as the test client.

## Run status

| Status | Meaning |
|---|---|
| `complete` | All six core files and all three metrics files are present and valid |
| `metrics_missing` | The core files are valid, but no metrics file exists. This is a normal state: runs saved before M4 and runs with no trades. `problems` gives the command that computes them. |
| `invalid` | A file is missing, unreadable or not the expected shape. The metrics files are only partly there, or don't describe this run. Or `manifest.json` belongs to another folder. `problems` lists each issue. |

## Results

**Tests:** 175 locally (CI runs the 162 that don't need local data).
- 47 new API tests on synthetic runs.
- 1 new real-data test: every saved run in `runs/` loads, and the served metrics equal
  the saved files.
- They cover:
  - every endpoint against the hand-computed M4 example week;
  - 11 kinds of broken files, each a 500 that names the file while the run list keeps working;
  - unknown runs and trades;
  - malformed and path-escaping run ids;
  - runs without metrics;
  - missing values served as null;
  - 8 kinds of invalid launch parameters;
  - a launch with no market data, a launch with no trades, a concurrent launch, a run-id
    clash and an engine failure;
  - the `serve` command's default host and its warning.

**Checked against real data:**
- A five-year run launched through HTTP gave the same files as the CLI reference run:
  - its trade, mark, equity, skipped, yearly and monthly files are byte-identical;
  - `metrics.json` is equal apart from run id and git state.
  - 263 trades, net ₹2,79,138.52.
- That launch took about 80 seconds.
- The drill-down on the worst trade (12 May 2026 expiry) shows its marks −₹154.65, ₹1,847.35,
  −₹10,837.40 and finally −₹41,067.44, matching M4.

## Key design decisions

1. **Read-only for saved runs.** GET requests only read files; they never recompute metrics.
   This keeps M4's rule that every number traces to a file on disk. The one write is
   `POST /api/runs`, which makes a *new* folder exactly as the CLI does. The `metrics`
   command remains the only way to (re)compute a run's metrics.
2. **Check everything before serving anything.** Each file is parsed into a strict model:
   unknown columns are refused, types are checked, and infinity is refused. A file that
   doesn't fit is a 500 naming the file and the first problem, never a partial answer. 500
   (not 4xx) because the request was fine; the saved data is at fault.
3. **One broken folder never breaks the list.** `GET /api/runs` checks each run separately
   and shows a broken one as `invalid` with its reasons.
4. **Missing values become null, never NaN.** An empty CSV cell becomes `null`. A `NaN` token
   in `metrics.json` (which strict JSON forbids, see R5) makes that file invalid.
5. **Older files are served as saved.** Metrics written before the M4 correction don't have
   its new fields, so the response leaves them out instead of inventing values.
6. **Run ids are checked before any path is built.** They must match `save_run`'s pattern.
   That rules out `..`, slashes and anything else that could read outside `runs/`.
7. **Launch is the CLI, not a copy of it.** `launch.py` calls the same `run_backtest`,
   `save_run` and `write_metrics`, with defaults taken from `ShortStraddle`, `CostConfig` and
   `RunConfig` rather than retyped. So the git state, dirty-tree warning, data hashes and
   resolved end date are recorded exactly as for CLI runs.
8. **One launch at a time.** A backtest reads the whole store, and two runs saved in the same
   second would get the same id. A second launch while one is running gets 409.
9. **Localhost by default.** There is no authentication, so `serve` binds to 127.0.0.1 and
   warns if told to bind anywhere else.

## Limitations

- **Launch is synchronous.** `POST /api/runs` returns only when the run has finished, which
  takes about 80 seconds for the full five years. There is no background job queue or
  progress reporting.
- **Only the short straddle can be launched,** with the parameters the CLI offers. There is no
  risk-free-rate parameter on launch; `nifty-backtest metrics --risk-free` recomputes that.
- **No authentication, CORS or rate limiting.** CORS will be added in M6, when the dashboard
  needs it.
- **No pagination.** The largest response (the full trade log) is about 300 KB.
- **No caching.** Files are re-read and re-checked on every request, so the run list costs a
  little more with every saved run.
- **A launch failing midway can leave a folder behind.** If metrics fail after a run is saved,
  the folder is kept and the error names the run; the list then shows it as
  `metrics_missing`.
- **One test-client warning is silenced in `pyproject.toml`.** Starlette's test client warns
  that it would prefer the `httpx2` package, which is not an approved dependency.
- **`/docs` loads its viewer from a CDN.** The page itself is served locally, but the Swagger
  UI scripts it uses come from FastAPI's default CDN, so viewing it needs internet access.

## Explain-back questions

1. A GET request for a run whose `metrics.json` is missing returns 409, but one whose
   `yearly.csv` alone is missing returns 500. Why are those different, and why is neither a
   404?
2. Why does the API refuse to serve a `trades.csv` that has one extra column it doesn't
   recognise, instead of just ignoring the column?
3. What stops `GET /api/runs/..%2F..%2Fsecret/trades` from reading a file outside `runs/`?
4. A run launched through `POST /api/runs` and one launched with `nifty-backtest backtest`
   produce identical files. Which design choice guarantees that, and what would break it?
5. Why does the run list show a broken run as `invalid` instead of failing the whole request
   with a 500?
