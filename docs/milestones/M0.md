# M0: Repository setup

## Demo

```bash
uv run nifty-backtest --version
uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest -v
```

Then open the repository's **Actions** tab on GitHub: the CI run for the latest commit should
be green. That green run is M0's "done when" condition.

The format check reports 13 files even though there are only 9 `.py` files. ruff 0.16 also
checks Python code blocks inside the Markdown files (README, CLAUDE.md, these notes).

## What was built

- **A uv project.** `pyproject.toml` declares the project, `uv.lock` pins every package version,
  and `.python-version` pins Python 3.12. uv downloaded its own Python 3.12.15, so the Pythons
  already on the machine (Homebrew 3.14, pyenv 3.11) are untouched.
- **Dev tools,** locked: ruff 0.16 (lint and format), mypy 2.4 (types) and pytest 9.1 (tests).
  All three are configured in `pyproject.toml`.
- **The package skeleton** in `src/nifty_backtest/`:
  - `cli.py`: the `nifty-backtest` command. So far it only has `--version`.
  - One sub-package per module boundary from spec §8: `marketdata`, `strategies`, `engine`,
    `costs`, `metrics` and `api`. Each holds only a docstring until its milestone.
- **Three placeholder tests** in `tests/test_cli.py`.
- **CI** in `.github/workflows/ci.yml`. It runs the same four checks on every push and pull request.
- **Repo files:** `.gitignore`, `reference/README.md` (rules for hand-maintained files), the
  README skeleton and this note.
- **Spec amendments** approved before M0. They are listed in CLAUDE.md §10.

## Key design decisions

1. **The lockfile is committed.** `pyproject.toml` says what we need, as version ranges.
   `uv.lock` records exactly which versions were installed. CI runs `uv sync --locked`, so it
   tests the same versions as your laptop. If the lockfile is out of date, CI fails instead of
   quietly picking different versions.
2. **Python 3.12.** It is the spec's minimum version and has the widest library support. Code
   that works on 3.12 also works on newer versions.
3. **src layout, plus pytest's importlib mode.** Tests import the *installed* package, not
   whatever folder happens to be on the path. A packaging mistake, such as a file left out of
   the build, therefore fails the tests instead of hiding.
4. **The version is written in one place.** It lives in `pyproject.toml`; `__version__` reads it
   back from the installed package, and a test checks that the two match.
5. **argparse for the CLI.** It is part of Python's standard library, so it adds no dependency.
   Each later milestone adds a subcommand.
6. **Strict from day one.** mypy runs in strict mode, so every function needs type hints. pytest
   runs in strict mode, so a typo in its config or a test marker is an error rather than a silent
   warning. Adding types to code that already exists is much harder than writing them as you go.
   I checked that the settings actually take effect: a deliberately bad file fails both mypy and ruff.
7. **CI matches local.** CI runs exactly the commands you run. It has read-only permissions.
   Both GitHub Actions are pinned to exact versions; `setup-uv` no longer publishes moving major
   tags such as `v10`.
8. **Empty sub-packages now.** The module boundaries are visible from the first commit, and each
   docstring says what will go there and in which milestone.
9. **`data/` is ignored, `reference/` is tracked.** Downloaded data is large and belongs to NSE,
   so it is never committed. Reference files are small, written by hand and sourced, so they need
   history and review like code. The leading `/` in the `.gitignore` rules ties them to the repo
   root. Without it, a rule such as `data/` would also hide any code folder named `data`.
10. **Test data policy (applies from M1).** CI uses small synthetic files with NSE's real columns.
    Tests on real data run only on your machine, and are skipped when the data cache is missing.

## Explain-back questions

1. `pyproject.toml` says `pytest>=9.1.1`, but `uv.lock` says exactly `pytest==9.1.1`. Why commit
   both files, and what does `--locked` protect against in CI?
2. Why does the code live in `src/nifty_backtest/` instead of directly in the repo root? What
   kind of mistake does that catch?
3. You type `uv run nifty-backtest --version`. What happens between pressing Enter and `main()`
   running? (Hint: `[project.scripts]`.)
4. CI runs four checks: `ruff check`, `ruff format --check`, `mypy` and `pytest`. For each, give
   one problem it would catch that the other three would miss.
5. Why is `data/` ignored by git while `reference/` is tracked? And why will CI tests use
   synthetic rows instead of real NSE rows?
