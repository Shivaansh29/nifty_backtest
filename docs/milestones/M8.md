# M8: Docker packaging and reproducibility

## Demo

Start (from the repository root, with Docker Desktop or Docker Engine + Compose v2 running):

```bash
mkdir -p data/processed runs studies
export GIT_COMMIT=$(git rev-parse HEAD)
export GIT_DIRTY=$([ -z "$(git status --porcelain)" ] && echo false || echo true)
docker compose up -d --build --wait
```

- Open http://127.0.0.1:8080 for the dashboard: the saved runs, the M7 research page, and the
  launch form.
- Open http://127.0.0.1:8080/docs for the API documentation (Swagger UI).
- `docker compose ps` should show both services as `running (healthy)`.
- Launch a run from the form. Its folder appears in `runs/` on this computer, and its
  `manifest.json` records the commit you exported.

Stop:

```bash
docker compose down
```

`down` removes the containers and their network. Runs, data and studies stay in their folders.

Checks:

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest
cd frontend && npm run typecheck && npm test && npm run build
NIFTY_DOCKER_TESTS=1 uv run pytest tests/test_docker.py    # builds and starts its own stack
```

## What was built

| File | What it does |
|---|---|
| [`Dockerfile`](../../Dockerfile) | **API image.** Python 3.12.15 with exactly the packages in `uv.lock` (no dev tools), the installed package and `reference/`. Runs one uvicorn worker as a non-root user. |
| [`frontend/Dockerfile`](../../frontend/Dockerfile) | **Dashboard image.** Builds the React app with Node 24.14.1 from `package-lock.json`, then serves `dist/` with unprivileged nginx 1.30.6. |
| [`frontend/nginx.conf`](../../frontend/nginx.conf) | Serves the dashboard and forwards `/api`, `/docs`, `/redoc` and `/openapi.json` to the API container. Adds security headers and cache rules. |
| [`compose.yaml`](../../compose.yaml) | Two services, health checks, start order, bind mounts, resource limits, hardening. The web port is published on 127.0.0.1 only; the API publishes no port. |
| [`.dockerignore`](../../.dockerignore), [`frontend/.dockerignore`](../../frontend/.dockerignore) | Allow-lists of what may enter each build. |
| [`.env.example`](../../.env.example) | Optional settings: port, folders, user ids, time zone. |
| `engine/runs.py`, `research/study.py` | Records the code version when git is not available (below). |
| [`tests/test_docker.py`](../../tests/test_docker.py) | Builds and starts the stack and tests it from outside (below). |
| `.github/workflows/ci.yml` | A third CI job, "Docker checks", runs those tests on every push. |

## Key design decisions

1. **Two images, one origin.**
   - nginx serves the built dashboard and forwards API requests to the API container.
   - The browser therefore sees one origin, as it does through Vite's proxy in development.
     The API still needs no CORS headers, and the frontend code is unchanged.
   - The API container publishes no port, so nginx is the only way in. Compose publishes
     nginx on `127.0.0.1` only.
2. **Pinned, locked, reproducible builds.**
   - Every base image is pinned by version **and** sha256 digest.
   - Python packages come from `uv sync --locked --no-dev`. Node packages come from `npm ci`.
   - uv 0.12.24, Python 3.12.15 and Node 24.14.1 are the same versions CI and local
     development use.
   - nginx 1.30.6 was released less than two weeks before M8. It is used anyway because it
     fixes five CVEs (nginx.org, CHANGES-1.30, 14 Oct 2026). 1.30 is nginx's stable line.
3. **Data stays on the host and is mounted, never copied.**
   - The build contexts are allow-lists: everything is excluded except the files each image
     needs. `data/`, `runs/`, `studies/`, `.env`, `.git` and caches cannot reach an image,
     even by accident. A test searches both finished images for them.
   - At run time the API mounts `data/processed` read-only, `studies/` read-only and `runs/`
     read-write.
   - The working directory is `/app`, laid out like the repository. The relative paths the
     code uses (`data/processed`, `runs/`, `reference/`) are therefore the same in both
     places, and a run launched in the container opens on the host and vice versa.
   - `create_host_path: false` makes a missing folder an error. Otherwise Docker would
     silently create an empty, root-owned folder.
4. **Recording the code version without git (D2).**
   - The image has no git and no `.git`. The commit is baked in at build time as
     `NIFTY_GIT_COMMIT` / `NIFTY_GIT_DIRTY`, from the `GIT_COMMIT` / `GIT_DIRTY` you export.
   - `_git_state()` uses git when it can. When git is unavailable it uses the baked values.
   - A run is recorded as clean **only** when a commit is present and `NIFTY_GIT_DIRTY` is
     exactly `false`.
   - Anything else records commit `unknown` (or the baked commit) with
     `uncommitted_changes: true`. A run is never marked clean when nobody checked.
   - `nifty-backtest study` refuses to run without git. A pre-registered study must show its
     plan files are committed, which needs git, so studies stay a host-only command.
5. **Hardening for a local tool.**
   - Both containers run as non-root users: the API as `NIFTY_UID` (default 1000), nginx as
     101.
   - Both have a read-only root filesystem, a small tmpfs `/tmp`, every Linux capability
     dropped, `no-new-privileges`, and memory, CPU and process limits.
6. **One API worker.** The "one launch at a time" lock (M5) is a lock in the API process's
   memory. A second uvicorn worker would have its own lock and allow two launches at once.
7. **Health checks and start order.**
   - The API is healthy when `/api/health` answers. nginx is healthy when `/healthz` answers.
   - The web service starts only once the API is healthy, and `up --wait` returns only when
     both are.
   - nginx re-resolves the API's address through Docker's DNS (`resolver 127.0.0.11` with the
     upstream in a variable). Restarting only the API therefore does not leave nginx
     forwarding to a stale address. A test restarts the API and checks this.
8. **Time zone.** Run ids are local timestamps, and a container's clock is UTC by default.
   Compose sets `TZ=Asia/Kolkata` (`NIFTY_TZ`), so runs from the host and the container sort
   together in one `runs/` folder. This changes only run ids, never any result.

## Verification

### Docker tests (`tests/test_docker.py`)

They build both images from scratch and start their own stack on port 18080, with
temporary folders and the synthetic week used by the engine tests. They check:

- **Configuration:** only the dashboard is published, and only on 127.0.0.1. Hardening is
  present on both services, and each mount is read-only or read-write as intended.
- **Health:** both services are healthy.
- **Users:** neither container runs as root.
- **Image contents:** neither image contains data, runs, studies, `.env` or `.git`.
  - The API image's `/app` holds only `.venv` and `reference/`, and `reference/` matches the
    repository.
  - The dashboard folder holds only `index.html` and `assets/`.
  - pyarrow's own sample `.parquet` test files inside its package are the one exception the
    search skips.
- **Writable paths:** only `runs/` is writable. The root filesystem, `data/processed` and
  `studies/` reject writes.
- **Dashboard delivery:** `index.html` and the assets are served with the right content
  types and cache rules, and security headers are set. A missing asset is a 404, not the
  dashboard.
- **API through the proxy:** health works. `/openapi.json` equals the committed
  `frontend/src/api/openapi.json`. `/docs` serves Swagger UI. The API's own 404 JSON comes
  back unchanged.
- **Container run equals host run:** a launched run is identical to the same run made
  outside Docker. Its commit is the one baked into the image.
- **Persistence:** after `compose down` and `up` the run is still served. After restarting
  only the API, the proxy still works.
- **Real data (local only, skips without the data cache):** a full five-year launch in the
  container is compared with the same launch on the host, and the served M7 studies equal
  the in-process API's.

### Container vs host results

Measured on the real five-year launch (`end = 2026-10-16`):

- **Identical byte for byte:** `trades.csv`, `marks.csv`, `equity.csv`, `skipped.csv`,
  `config.json` and `manifest.json`. That covers every trade, every daily mark, the equity
  curve and the data hashes.
- **Equal to 12 significant digits:** the statistics derived from the daily series (Sharpe,
  Sortino, drawdown, per-year and monthly figures).
  - The largest relative difference was 3.4e-13, in the last one or two of 17 printed
    digits.
  - The cause is numpy on Linux and on macOS adding long columns in a different order, and
    floating-point addition is not associative.
  - This is the same tolerance the dashboard fixtures use since M6.
  - The reconciliation check (which should be ~0) was 5.8e-11 Rs in the container and
    1.2e-10 Rs on the host: both are rounding noise.

### Resources and launch time

| Measurement | Value |
|---|---|
| API memory during a five-year launch | peak about 305 MiB (limit 2 GiB) |
| Launch time on the host (macOS, in-process) | about 100 s |
| Launch time in the container, data on a Docker volume | 107 s |
| Launch time in the container, data bind-mounted (Docker Desktop for macOS) | about 270 s |

- The bind-mount slowdown is Docker Desktop's macOS file sharing, not the CPU or memory
  limits. The same launch with no CPU limit took as long.
- Linux hosts (and CI) use native bind mounts.
- nginx waits up to 900 s for a launch to answer.
- The approved design keeps bind mounts. Copying data into a volume would duplicate the
  cache and need a sync step.

CI runs the same Docker tests in the "Docker checks" job. The real-data test skips there,
because CI has no NSE data.

Problems found while testing, and fixed before the commit:
- **The image search needed root.** As the unprivileged user, `find` could not read a few
  system folders and failed. The throwaway inspection container now runs as root. It also
  skips pyarrow's own sample `.parquet` files.
- **The host comparison ran outside git.** The in-process host run moved into a temporary
  folder, so it recorded commit `unknown`. It now gets the same baked-in commit as the
  image. The test's git lookups use `git -C <repo>`, so they work from any folder.
- **The launch timeout.** The first real-data launch through nginx returned 504 after the
  original 300 s read timeout. The timeout is now 900 s; see the launch-time table above.
- **Statistics compared byte for byte.** That comparison failed on 1e-13 differences, as
  explained above; those files are now compared to 12 significant digits.
- **Run ids in UTC.** They are now in Indian time (`TZ`).

## Security limitations

- **No authentication or TLS.** Anyone who can reach port 8080 can read every run and launch
  new ones. The stack is safe only because the port is bound to 127.0.0.1. Do not publish it
  on other interfaces, or behind a public address, without adding authentication, TLS and
  access control first.
- **Launch is a denial-of-service lever.** One launch at a time is enforced, but each one
  uses CPU for minutes. On a shared machine, anyone with access could keep the API busy.
- **Swagger UI loads its scripts from a CDN** (FastAPI's default), so `/docs` needs internet
  access and trusts that CDN. The dashboard itself loads nothing external.
- **No Content-Security-Policy header.** The basic headers are set (`nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`). A CSP was left out because
  Swagger UI's CDN scripts would need exceptions.
- **Images are pinned, not patched automatically.** The digests keep builds reproducible, but
  security fixes in the base images arrive only when someone updates the pins.
- **On Linux, set `NIFTY_UID` / `NIFTY_GID` to your own ids.** Otherwise run folders the API
  writes belong to uid 1000. Docker Desktop on macOS and Windows maps ownership itself.
- **Studies are host-only.** The container serves studies read-only. Running one needs git,
  so `nifty-backtest study` runs on the host.

## Explain-back questions

1. The browser loads the dashboard from `127.0.0.1:8080` and calls `/api/runs`. Follow that
   request: which container answers, how does it reach the API, and why does the API need no
   CORS headers?
2. A run launched inside the container records a git commit, but the image has no git. Where
   does the commit come from? What is recorded if you build without exporting `GIT_COMMIT`,
   and why is that run never marked clean?
3. Why do `trades.csv` and `equity.csv` match the host byte for byte while `metrics.json`
   only matches to 12 significant digits? Why is that not a sign of a calculation
   difference?
4. Someone puts a `.env` with an API key and a `data2/` folder in the repository. Why can
   neither end up in an image, and which test would catch it if the ignore files were
   changed?
5. Why does compose run exactly one uvicorn worker? What would break with four?
